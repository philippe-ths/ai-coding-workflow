Loki-side accumulation for v3.0.0 begins at adoption. **Earliest realistic re-attempt: ~30 days after v3.0.0 merges and is adopted in at least one external repo, conditional on baseline harness runs in the same window.**

## Findings that are not proposals

Five observations surfaced by running the gate. None meet the disqualifying-conditions bar for a proposal; they are recorded here so the next review does not rediscover them.

1. **The baseline harness has never been run for any released workflow version.** The 2026-04-19 worked example noted 6 mock-agent JSONs for v2.9.0; those are no longer present. The harness exists and is wired but no real run has been preserved.
2. **`ruleset_hash` is by design ai-coding-workflow-only.** Condition 4 of the gate, read literally against the current sample, is unsatisfiable for sessions originating outside this repo. This is a tension between the gate as written and the emission policy; it should be reconciled in `design/decisions/evaluation.md`, not by changing emission.
3. **Cross-version Loki comparison of external-repo sessions conflates ruleset change with repo change.** v2.15.0 sessions come from `ai-coding-workflow` + `FCP-Auto-Editor`; v2.16.0 sessions come from `Eleve` only. Differences between the two versions in any Loki metric cannot be attributed to the workflow change alone.
4. **`workflow_version` on external repos reflects that repo's local `ai-workflow.md` version.** It indicates adoption status, not which version of this repo's workflow was running. Useful for tracking rollout but not for paired comparison.
5. **Loki query-range limit is 30 days; the gate's "real sessions per version" needs to be evaluated within that window or via repeated paginated queries.** Current process documentation does not mention this constraint.
